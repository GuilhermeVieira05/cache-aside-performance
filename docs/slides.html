Fundamentos

Por que o cache é mais rápido?

Tudo é sobre onde os dados estão fisicamente. Cada nível da hierarquia de memória tem latência radicalmente diferente:

🔵 L1/L2 CPU Cache
1 – 4 ns
dentro do chip
🟢 RAM (Redis)
~100 ns
memória principal
🟡 SSD NVMe
~100 µs
1.000× mais lento
🔴 PostgreSQL query
10 – 100 ms
parse + disco + rede
💡

O Redis armazena tudo em RAM — sem parsing SQL, sem planejamento de query, sem acesso a disco, sem locks. Um GET no Redis custa 100 nanosegundos. Uma query no Postgres custa até 100.000× mais.

Fundamentos

Por dentro do Redis — não é só RAM

A memória explica a velocidade bruta, mas é a arquitetura do Redis que elimina os gargalos que tornam um banco relacional lento sob carga:

🧵

Single-thread, sem locks

Um único loop de eventos executa um comando por vez, de forma atômica. Sem locks, sem troca de contexto, sem condições de corrida — justamente o gargalo que derruba bancos sob alta concorrência.

🗂️

Estruturas em memória

Strings, hashes e sorted sets nativos, escritos em C com operações O(1). Buscar uma chave é um lookup direto numa hash table — nada de varrer linhas ou percorrer índices em disco.

🚫

Sem query planner

Não há SQL para interpretar nem otimizador escolhendo plano de execução. A etapa parse → plano → execução do PostgreSQL simplesmente não existe: o acesso é direto pela chave.

🔌

I/O multiplexado

Uma só thread atende milhares de conexões com I/O não-bloqueante (epoll). Com pipelining, vários comandos viajam numa única ida-e-volta de rede, amortizando a latência.

⚙️

RAM é só metade da história. É a ausência de parsing SQL, locks e disco — somada a estruturas O(1) e a um modelo single-thread atômico — que faz cada GET custar ~100 ns de forma previsível, mesmo com milhares de clientes simultâneos.

⚖️O trade-off do MISS

O MISS custa ~35% a mais que ir direto ao banco — é o preço de gravar o resultado no cache. Mas cada HIT seguinte é ~37% mais rápido que a query. Já na 2ª leitura idêntica o cache empata; da 3ª em diante, a economia só cresce.

O ganho mais sólido e reprodutível do cache é tirar carga do banco: com ~90% de hit rate, 9 em cada 10 leituras nem chegam ao PostgreSQL. No servidor, uma leitura do cache custa ~1 ms contra ~10 ms indo ao banco — e essa folga vira tempo de fila economizado quando o tráfego cresce.

Aí o cache brilha. Com o banco no limite, cada query enfrenta fila. O cache desvia 9 em 10 leituras e a mediana despenca ~25×.

⚖️

O valor do cache é proporcional à pressão sobre o banco. Ele não multiplica a vazão — o throughput fica praticamente igual (±7%) nos dois casos. O que ele faz é proteger o banco e estabilizar a latência justamente quando o tráfego aperta.

Análise Arquitetural

Trade-offs e Consistência

⏰ Consistência Eventual (TTL)

Com TTL de 5 min, usuários podem ver dados levemente desatualizados até o cache expirar. Mitigação: invalidação explícita em toda escrita garante consistência pós-PUT/DELETE.

🗑️ Invalidação Explícita

Todo PUT/DELETE chama CacheService.invalidate(). A chave é removida imediatamente — sem esperar o TTL. Próxima leitura recarrega o dado atualizado.

❄️ Cold Start

Na inicialização ou após reset, o cache está vazio. As primeiras requisições são sempre MISS e mais lentas. Em produção: warm-up prévio ou cache persistente.

🌊 Cache Stampede

Se muitas requisições chegam exatamente quando uma chave expira, todas vão ao banco simultaneamente. Mitigação: TTL com jitter aleatório, ou lock de recomputação (mutex).

🔄 Quando NÃO usar Cache Aside

Dados com consistência forte obrigatória (saldo bancário, estoque crítico). Nesses casos: write-through ou read-through são mais adequados.

💡 Degradação Graciosa

Se o Redis cair, o CacheService captura o erro e passa direto ao banco com status ERROR. O sistema não para — degrada para o comportamento sem cache.

Conclusão

O que aprendemos

  • ✓Cache-aside não é só otimização — é uma decisão arquitetural com implicações de consistência, complexidade e operação
  • ✓A diferença entre RAM e disco — 100.000× mais lenta — é a razão fundamental pela qual o cache funciona
  • ✓Medido no nosso stack: −90% de consultas ao banco e leitura do cache em ~1 ms (vs ~10 ms no banco), com a mesma infraestrutura
  • ✓O ganho de latência é proporcional à pressão sobre o banco: aparece sob carga, quando o banco vira gargalo — e não com o banco ocioso
  • ✓Invalidação explícita é fundamental para consistência pós-escrita — sem ela, dados desatualizados comprometem a API
  • ✓Observabilidade com Grafana + Loki permite ver HIT/MISS/INVALIDATE em produção em tempo real
